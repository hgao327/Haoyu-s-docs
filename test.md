### 1. Current design: n-step off-policy with pre-production

In addition to the existing on-policy loop, off-policy mode (`offpolicy_steps > 0`) introduces:

- **Pre-production of historical data**
   Before the main training loop starts, we run rollouts for up to `offpolicy_steps` initial batches and push their training examples into the shared training queue.
   This guarantees that, at the very beginning of training, the learner is already consuming data generated by **older policy versions**, not the most recent one.

- **Version gap: consume old, produce new**
   During each iteration of the main loop:

  - The **training side (consumer)** reads samples that were generated by an **earlier policy version**, and updates the current model on that “stale” data.
  - The **rollout side (producer)** uses the **latest policy version** to generate trajectories for a newer batch and appends them to the queue.

  We enforce a simple invariant:

  > All rollouts for a batch must finish under a single fixed policy version, and **only after those rollouts complete** do we allow a `sync_weights()` to create the next version.

  At any time we are **training on old-version data while producing new-version data**, with the delay controlled by `offpolicy_steps`, which implements n-step off-policy behavior in a controlled way.

------

### 2. Future design (v2): fully decoupled off-policy pipeline

A future iteration will further generalize this into a **fully decoupled producer–consumer pipeline**:

- **Version-tagged data**
   Each batch of rollouts will be tagged with the **policy version** that generated it. The producer can continuously generate rollouts using its current version without being aware of the consumer’s progress.

- **Consumer-driven sync and off-policy filter**
   The consumer will continuously pull samples from the queue and train, checking the version tag to know which policy produced the data. It will also compare the version gap against the configured `offpolicy_steps` and **only use samples whose lag w.r.t. the current policy is within that bound**.

  When the consumer finishes training on a logical batch (or a configured amount of data), it will issue a **weight sync signal**:

  - The rollout orchestrator stops accepting **new** tasks for the current version boundary.
  - It waits for all **in-flight rollouts** under the current version to complete.
  - Once all rollouts for that version have finished, the system performs `sync_weights()` and bumps the policy version, after which producers resume with the new version.

This v2 design keeps producer and consumer **fully asynchronous**, while the explicit version tags, the `offpolicy_steps` filter, and the sync protocol together ensure that:

- each batch’s rollouts are internally version-consistent, and
- training always knows exactly how “old” the data is and only learns from batches that satisfy the desired n-step off-policy constraint.

------

### 3. Future design (v3): suspend/resume-aware off-policy

When the inference stack (e.g., sglang) supports **suspend / resume**, we can further relax the sync constraint:

- At version boundaries, the rollout orchestrator can **suspend** in-flight rollouts, perform an immediate `sync_weights()`, and then **resume** those rollouts under the new weights, instead of waiting for them to finish.
- Rollouts (or segments) will carry version metadata; the consumer still applies the `offpolicy_steps` constraint by checking the version gap and only training on data within the allowed lag.

This keeps the same off-policy semantics, but removes the need to block on long-tail rollouts before syncing weights.
